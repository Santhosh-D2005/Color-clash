# Publishing to the Play Store

Two halves: creating a signing key that only you hold, and getting a signed
bundle built. Everything below can be done from a phone.

---

## Trademark status — resolved

An earlier version of this document opened with a blocker: the artwork shipped
with the project carried another company's registered wordmark, and publishing
it would have risked the listing being pulled.

That is fixed. The app is **Color Clash**, every image is generated from
original vector sources this project owns, the card faces are drawn in CSS, and
the sound is synthesised at runtime — so there is no third-party asset in the
build to license. `npm run audit:brand` runs in CI and fails if the old mark
reappears.

The full record, including the licence status of every asset class and the two
things the audit cannot check by itself, is in `docs/BRANDING.md`.

## 1. Create your signing key

**Do this yourself. Never accept a keystore generated by someone else** — whoever
holds it can publish updates to your app. It should exist only on your device
and in your own backups.

In Termux:

```bash
pkg install -y openjdk-21
keytool -genkeypair -v \
  -keystore colorclash-release.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias clash-upload
```

It asks for a password (twice) and some identity fields — name, organisation,
city, country. They appear in the certificate, not in the store listing.

Two things to understand:

- **`-validity 10000`** is about 27 years. Play requires a key valid well past
  2033; do not shorten this.
- **Back the file up.** If you lose `colorclash-release.jks` _and_ have not enrolled in
  Play App Signing, you can never update your app — you would have to publish a
  new listing under a new package id and lose your installs and reviews.

### Play App Signing

When you create the app in the Play Console, opt in to **Play App Signing**
(it is the default for new apps). Google then holds the key that actually signs
what users install, and the key you just made becomes your _upload key_ — used
only to prove uploads come from you. If you lose an upload key, Google can reset
it. That is the safety net, and it is worth taking.

## 2. Store the key as repository secrets

The workflow needs the keystore as text, so encode it:

```bash
base64 -w 0 colorclash-release.jks > keystore.b64
cat keystore.b64
```

Copy that output. Then on GitHub: **Settings → Secrets and variables → Actions →
New repository secret**, and add four:

| Secret                      | Value                                                                        |
| --------------------------- | ---------------------------------------------------------------------------- |
| `ANDROID_KEYSTORE_BASE64`   | the base64 text you just copied                                              |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password                                                        |
| `ANDROID_KEY_ALIAS`         | `clash-upload`                                                               |
| `ANDROID_KEY_PASSWORD`      | the key password (same as the store password unless you set a different one) |

Then delete `keystore.b64` from your device — the plain base64 is as sensitive
as the keystore itself:

```bash
rm keystore.b64
```

Repository secrets are encrypted, are not exposed to workflows triggered from
forks, and are masked in logs. The `.jks` file itself is never committed; the
workflow decodes it into the runner's temporary directory and deletes it
afterwards.

## 3. Build the release

**Actions → Build signed Android release → Run workflow.** Enter a version name
(`1.0.0`).

The workflow refuses to start if any secret is missing, runs the typechecker
and the full test suite before building, and verifies with `apksigner` and
`jarsigner` that the outputs really are signed — an unsigned release build is
the exact failure this is designed to catch.

Download the **color-clash-release** artifact. It contains:

- `color-clash-1.0.0.aab` — upload this to the Play Console
- `color-clash-1.0.0.apk` — sideload this to test the identical build first

### Version codes

`versionCode` comes from the workflow run number, so it increases automatically
and never repeats — Play rejects a bundle whose version code it has already
seen. `versionName` is what users see, and you set it per run.

### Target API level

`tools/android-release.ts` pins `compileSdk` and `targetSdk` (currently 35)
rather than inheriting whatever Capacitor ships, so a dependency bump cannot
silently drop you below Play's requirement. Google raises that requirement
annually — check the current minimum in the Play Console and change the two
constants at the top of that file.

## 4. The Play Console side

Beyond the bundle, a listing needs:

- A developer account (one-off registration fee) and identity verification
- App name, short and full description, and a privacy policy URL — required
  even for an app that collects nothing
- A 512×512 icon, a 1024×500 feature graphic, and at least two phone
  screenshots
- The Data Safety form — this app collects nothing and has no analytics wired
  up, so it is a short form, but it is mandatory
- A content rating questionnaire
- For the online mode: note that gameplay is peer-to-peer over a server you
  run. If you host a public server, that changes your data-handling answers.

Expect review to take a few days for a first submission.

## Testing without publishing

You do not need any of the above to play the game or share it with friends:

- **Home-screen app** — `npm run build:pwa`, serve `dist/pwa`, install from
  Chrome. No signing, no store.
- **Debug APK** — the `Build Android APK` workflow produces a sideloadable
  build with no secrets at all.
- **Internal testing track** — once you do have a Play account, this
  distributes to up to 100 testers by email without a public listing or a full
  review.
